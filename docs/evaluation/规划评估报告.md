# MoGrab 规划评估报告

评估对象是《MoGrab 项目规划书》，67 个正文章节加 9 个 Build & Release 子节。
方法是逐节读完，把章节之间对不上的地方挑出来，再按"能不能照着写代码"的标准
过一遍每个设计决策。日期 2026-10-04。

结论：架构方向没问题，不用动。但工程细节收敛得不够 —— 有四处互相矛盾到
没法开工，另外七处会影响架构正确性。这些都在这轮里定了，下面逐条说。

---

## 一、整体印象

先说好的地方。

**架构方向是对的。** API-First 加声明式书源这个组合，准确避开了 Legado 那套
"历史书源兼容地狱"。规划书里那句话说得挺到位：不追求兼容所有书源，而是建立
自己的规范。这是想清楚了的。

**边界意识少见。** §61 专门列了一张"禁止越权"的表，比如 Exporter 不许请求网络、
Source 不许碰数据库。个人项目里很少有人会写这个，而且写了还愿意遵守的就更少。
后面实现的时候我基本是照着这张表在拆模块。

**范围控制住了。** §2.2 明确列了非目标：不破解验证码、不绕付费墙、不做分布式。
这类"不做什么"的清单比"要做什么"更有价值，因为它能挡住后来的需求膨胀。

**成功标准定得好。** §63 说核心指标是"新开发者能不能在几十分钟内写出第一个
可运行的 Source"，而不是"支持多少网站"。这个判断是对的，生态型项目就该这么看。

问题主要在另一头：**细节的收敛度不够**。表现是三种情况 —— 同一个东西在几处
写得不一样；提出了要求但没说怎么满足；给出了选项但没做选择。

第三种最麻烦。比如 §58 写"selectolax / lxml"，看起来是给了灵活性，
实际上是把这个决定推迟到了写代码的时候。而写代码的人当时做的决定，
就变成了事实上的契约，后面没人知道当初为什么这么选。

下面按严重程度分。P0 是开工前必须定的，P1 影响架构正确性，P2 影响质量和体验，
P3 是完善项。

---

## 二、P0：开工前必须裁决

### P0-01　目录结构在三处写得不一样

规划书给了三套仓库结构，互相冲突：

- §4：`packages/` 下七个包，`mograb-core` / `mograb-source` / `mograb-storage` /
  `mograb-http` / `mograb-parser` / `mograb-task` / `mograb-exporter`
- §5：单个 `packages/mograb-core/mograb/`，里面分
  `domain` / `source` / `network` / `task` / `storage` / `content` / `export` /
  `config` / `logging`
- §59：`packages/` 下七个目录，`core` / `source` / `network` / `parser` /
  `task` / `storage` / `exporter`，没有包名规范

不只是数量对不上。§4 叫 `mograb-http`，§59 叫 `network`；§4 和 §59 都没有
`content`，§5 有。这三套没法调和，必须选一个。

**怎么定的**：采用 uv workspace，一个核心包加两个应用。

```
packages/mograb/     核心库，内部按 §5 的模块划分
apps/cli/            mograb-cli
apps/api/            mograb-api
apps/desktop/        Electron
```

不用 §4/§59 的七个独立包，理由是那在当前阶段属于过度设计。七个包意味着七份
`pyproject.toml`、七组版本号、复杂的跨包依赖约束，换来的只是"理论上可以单独
复用"。但 network、task、storage 这几个模块本来就是为同一个产品的同一条流程
服务的，不存在单独复用的场景。为不存在的需求付出持续成本不划算。

§5 的模块划分是三者里最具体的，而且和 §59 的目录名基本同构，所以拿 §5 的划分
放在 §59 的 `packages/` 语义下，算是个自然的融合。

另外模块边界这件事，不一定要靠包边界来保证。§61 要求的那些边界（比如
Exporter 不许请求网络），靠导入约束一样能守住 —— `mograb.export` 不 import
`mograb.network` 就行。包边界提供的强制力并非不可替代。

细节写在 [ADR-0001](../architecture/decisions/ADR-0001-monorepo-layout.md)。

### P0-02　`version` 字段有两种含义

同一个字段名在三个地方意思不同：

| 位置 | 写法 | 实际含义 |
|------|------|---------|
| §7 书源示例 | `version: 1` + `version_name: 1.0.0` | `version` 是规范版本 |
| §13 Source 元数据 | `version: 1.2.0` | `version` 是书源版本 |
| §53 版本兼容 | `version: 1` + `engine.min_version` | `version` 是规范版本 |

§7 想用 `version` + `version_name` 区分，但这个名字本身就不好懂 ——
`version_name` 听起来像"版本的名字"，不像"书源版本"。而且它和 §13、§53 直接矛盾。

**为什么这是阻断性问题**：§53 存在的意义就是"防止新版 Source 被旧 Core
静默解析错误"。它的检查逻辑是先看 Schema 版本，再看引擎兼容性。如果加载器
分不清 `version: 1` 到底是规范版本还是书源版本，那最坏的情况是把它当成书源版本
1，于是 Schema 检查被整个跳过，旧引擎会去解析新版书源，产生错误的提取结果 ——
而且不报错。这正好是 §53 要防的事。

**怎么定的**：拆成两个字段，名字自解释，类型也不同。

```yaml
spec_version: 1      # 整数，规范版本
version: 1.0.0       # 字符串，书源自己的语义化版本
```

类型差异本身就是一道防线：`version: 1` 会被 SemVer 正则拒掉，报错信息也能
写清楚。细节在 [ADR-0002](../architecture/decisions/ADR-0002-source-version-fields.md)。

### P0-03　数据目录也说了两处

§23 写 `~/.mograb/`，但同一节里又说"Windows 建议使用系统标准用户数据目录，
而不是强制使用 `~/.mograb`"—— 自己就否定了自己。§57.4 则写 `%APPDATA%/MoGrab/`。

**怎么定的**：最初按 `platformdirs` 解析平台标准目录做了（Windows 走
`%APPDATA%\MoGrab`，Linux 走 `~/.local/share/MoGrab`）。后来改成了便携模式 ——
所有数据放在程序目录下的 `data/` 里，不写系统目录。

改的原因有两个。一是这个项目定位是个人工具，用户更可能想要"绿色版"：
拷走就能用，删掉就干净。二是规划书 §57.4 强调"升级程序不得删除用户数据"，
而数据就在程序目录旁边的话，这件事天然成立，不需要额外写升级逻辑。

`MOGRAB_HOME` 环境变量可以覆盖数据目录位置，测试和特殊部署用得上。

### P0-04　四份规范还没冻结

§66 自己说"正式开始编码前，优先冻结下面四份文档"，还给了优先级顺序：
Source Spec → Domain Model → Storage → API。但规划书正文里这四份规范的内容
散在 §6 到 §12、§23 到 §30 各处，而且带着上面那几个 P0 级的矛盾。

§60 又要求"Source Specification 优先于一切"。规范本身有歧义的话，
后面所有实现都建在不稳的地基上。

**怎么定的**：这轮产出了四份文档，矛盾全部消解：

- `docs/source-spec/source-spec-v1.md`
- `docs/domain-model/domain-model-v1.md`
- `docs/storage/storage-v1.md`
- `docs/api/api-v1.md`

## 三、P1：影响架构正确性

### P1-01　任务状态机只有状态，没有转移规则

§17 列了七个状态（PENDING / RUNNING / PAUSED / SUCCESS / FAILED / RETRYING /
CANCELLED），但没写谁能转到谁。§18 的流程图描述了正常路径，异常路径
（PAUSED 能不能直接取消、RETRYING 失败后去哪）一个字没提。

状态机是任务系统的核心不变量。没有形式化定义，实现的时候就容易写出
"从 SUCCESS 转回 RUNNING"这种漏洞，而且没法针对性写测试。

**怎么定的**：写成一张转移表，并且规定 `Task.transition_to()` 是唯一的
状态变更入口，非法转移抛异常。

```
PENDING   → RUNNING | PAUSED | CANCELLED
RUNNING   → PAUSED | RETRYING | SUCCESS | FAILED | CANCELLED
PAUSED    → PENDING | RUNNING | CANCELLED | FAILED
RETRYING  → RUNNING | FAILED | CANCELLED
SUCCESS   → 终态
FAILED    → 终态
CANCELLED → 终态
```

顺带定了一条：**终态不可逆**。重试是创建一个新任务，不是把旧任务复活。
这样任务历史就是不可篡改的，对得上 §39 对数据一致性的要求。

### P1-02　说了"必须提供失效策略"，但没说策略是什么

§16 列了缓存分层和缓存键的组成，然后写"同时必须提供失效策略"。就这一句，
后面没有了。

没有失效策略的缓存会出问题：站点更新了但读到旧内容，用户还没法自己清。
增量更新场景下更麻烦 —— 目录变了但正文缓存没失效，会下载到过期的正文。

**怎么定的**：三层。

- 条目级 TTL。列表页和详情页 30 分钟，正文页 7 天。
- 显式清除。对应 `mog cache clear` 和 `clear-source`。
- 容量淘汰。超过 `cache.max_size`（默认 5GB）按 LRU 淘汰。

缓存键里必须带 `source_id` —— 不同书源对同一个 URL 的规则不同，不能共用缓存。
这一条规划书没写，但很关键。

### P1-03　并发模型三处对不上

§15 写 `network.concurrency: 2`（按书源），§35 写 `[download] concurrency = 4`
（全局），§38 写 Global = 8、Source A = 2、Source B = 4。三处的数值、命名、
语义都不一样，也没说这两个层级怎么叠加。

**怎么定的**：明确成两级独立约束，取交集。

```
实际并发 = min(全局并发, 本源并发)
```

配置项统一叫 `download.concurrency`（全局）和 `download.per_source_concurrency`
（单源默认值，可以被书源里的 `network.concurrency` 覆盖）。
实现上用 `SourceLimiterRegistry` 按 `source_id` 维护独立限流器，
保证 A 源和 B 源互不影响。

### P1-04　领域模型少了几个字段

§27 要求 EPUB 元数据包含 `language`，§33 要求书架显示章节数，但 §6.2 的
`Book` 模型里没有 `language`、`word_count`、`chapter_count`、`cover_path`。

这种缺失在实现到那一步时才会暴露，而那时候补字段就得改数据库 schema，
要写迁移。

**怎么定的**：补上，并且分清哪些是书源给的、哪些是程序算出来的。

| 字段 | 来源 |
|------|------|
| `language` | 书源提供，可为空。EPUB 元数据要用，默认 `zh-CN` |
| `word_count` | 程序统计，书源不许写 |
| `chapter_count` | 程序统计 |
| `cover_path` | 封面下载后的本地路径，和 `cover_url` 是两回事 |

### P1-05　两个站点现实问题没覆盖

**编码**。§8.1 的 Request 里有 `encoding` 字段，但没说默认行为是什么。
中文小说站大量用 GBK / GB2312，而且经常不声明 charset。这个不处理，
第一次抓真实站点就会看到乱码。

**目录倒序**。部分站点的章节目录是倒序的（最新章节在前），§6.3 的 `index`
字段没说这种情况怎么处理。

这两个都不是"可选优化"，是第一次跑真实数据就会撞上的问题。

**怎么定的**：

编码探测按 `响应头 charset` → `meta charset` → `meta http-equiv` → `utf-8`
的顺序，并且把 `gb2312` 和 `gbk` 统一提升成 `gb18030`（前两个是它的子集，
用超集解码可以避免生僻字失败）。书源可以用 `request.encoding` 强制覆盖。

目录倒序在 `ResultSpec` 里加了 `reverse: bool`，书源声明，引擎提取后统一翻转。

顺带踩到一个坑：把 bytes 直接丢给 `lxml.html.fromstring`，lxml 会自己探测编码，
对没声明 charset 的中文页面会退化成 latin-1，出来是乱码。必须先按探测到的编码
解码成 str 再解析。这个 bug 是测试抓出来的。

### P1-06　进程崩溃后残留的任务没人管

§39 讨论了"下载成功但数据库没保存"，但没说反过来的情况：进程被强杀
（用户关窗、断电、OOM）之后，库里那些 RUNNING / RETRYING 的任务怎么办。

不处理的话，重启后界面显示"正在运行"，但实际上没有任何协程在跑。
用户看到永久卡住的任务，也没法重新触发。

**怎么定的**：`TaskManager.start()` 的时候做一次孤儿恢复，把所有
RUNNING / RETRYING 标成 FAILED，错误码 `INTERRUPTED`，让用户自己决定要不要重试。

为什么不自动重跑：崩溃原因未知，可能是源站封了，也可能是磁盘满了。
自动重跑可能造成重复请求，或者再崩一次。交给用户判断更安全。

`Task` 模型里留了 `resume_cursor` 字段，将来要做真正的断点续传可以用。

### P1-07　导出接口有同步和异步两个版本

§26 把导出器定义成同步接口：

```python
async def export(book: Book, target: Path) -> ExportResult: ...
```

但 §29 又给了 `POST /exports` 加 `GET /exports/{id}` 的异步作业语义 ——
创建的时候返回一个 id，之后再查状态。

两套并存的话，API 层和导出层的职责会糊掉。同步的话，几千章的大书生成 EPUB
会把请求阻塞到超时；异步的话，`ExportResult` 里的 `path` 在创建时还不知道。

**怎么定的**：异步作业。`POST /exports` 立刻返回 `{id, status: "pending"}`，
导出作为 `TaskType.EXPORT_BOOK` 任务执行，复用同一套状态机。
底层的 `Exporter` 协议保持 §26 的签名不变 —— 它描述的是"执行一次导出"，
由 Task Worker 调用。

## 四、P2：影响质量和体验

**P2-01　SSE 只有单任务流。** §30 只定义了 `GET /tasks/{id}/events`，
但 §33 的任务页要展示全部任务的实时进度。补了 `GET /api/v1/tasks/events` 聚合流。

**P2-02　本地 API 的信任边界没定义。** §50 说"第一版不需要复杂认证，
因为默认只监听 localhost"。但 localhost 不等于安全 —— 任何本机进程都能访问，
包括浏览器里的恶意页面。浏览器可以发简单请求（不需要预检）打到
`127.0.0.1:48721`，这就是本地 CSRF。

现在做的：CORS 收紧到只允许 `http://127.0.0.1:*`、`http://localhost:*` 和
`file://`。但光靠 CORS 挡不住简单请求，所以记了个待办：v0.4.0 正式引入 API 的
时候必须加随机 token，写进 `config.toml`，CLI 和桌面端读它。

**P2-03　Electron 安全基线没提。** §32/§33 讲了桌面端要做什么，但没讲怎么配。
骨架里直接开了 `contextIsolation: true`、`nodeIntegration: false`、
`sandbox: true`，CSP 只放行本地 API，渲染进程只能通过 preload 暴露的最小接口访问后端。

**P2-04　解析器选型没定。** §58 写的是"selectolax / lxml"。
定了用 `lxml`（配 `cssselect` 和内置 XPath），因为 §8.2 要求支持 XPath，
而 selectolax 不支持。一个引擎同时覆盖 CSS 和 XPath，`ExtractRule` 就只需要
一套语义，不用维护两套可能不一致的行为。selectolax 留作可选加速依赖。

**P2-05　EPUB 生成库没选，而且常用库有许可证问题。** §27 要求生成规范 EPUB，
§58 的技术栈里没有 EPUB 库。常见选择 `ebooklib` 是 AGPL-3.0，而本项目是
GPL-3.0-only。虽然 GPLv3 §13 允许和 AGPLv3 组合，但组合后整体要承担 AGPL 的
网络分发义务 —— 谁把 MoGrab 部署成网络服务，就得向用户提供源码。
对"个人工具"这个定位来说，这个合规负担不匹配。

定了自研。EPUB 本质就是 ZIP 加 XHTML 加 OPF，大概两百行，可控且没许可证问题。
测试里验证了结构规范，比如 `mimetype` 必须是第一个写入的且不压缩的条目。
细节在 [ADR-0003](../architecture/decisions/ADR-0003-parser-and-epub-deps.md)。

**P2-06　没有数据库迁移工具。** §24 定义了 8 张表，v1.0 目标要求"迁移稳定"，
但 §58 的技术栈只列了 SQLAlchemy。加了 Alembic。

**P2-07　CLI 退出码没定义。** §31 说要支持退出码但没给约定。补了七个：
0 成功、1 一般错误、2 参数错误、3 未找到、4 校验失败、5 网络错误、130 用户中断。

**P2-08　日志轮转没定。** §36 列了结构化字段和分流文件，没说轮转和保留。
长期跑会撑爆磁盘。补了单文件 10MB、保留 5 份。

**P2-09　文档编号重复，内容也有重复。** 正文有个 `# 57. MVP 版本规划`，
文末又有个 `# 57. Build & Release`（用了 57.1 到 57.9 的子编号），
后面的 58 到 67 和 57.x 混在一起，引用的时候说不清指哪个。
另外 §4 和 §59 的目录结构重复描述且不一致，§57 和 §60 内容高度重叠。

建议文末那章改成 68，或者整体重排。本仓库的 `docs/` 是按主题组织的，
不受原编号影响。

## 五、P3：完善项

- **P3-01** §9 的能力检查示例措辞有歧义。"而不是 `source.search()`"
  容易被读成"禁止调用方法"。正确的规则是*不得假定能力存在*，
  有能力的时候调用完全合法。已经在 `SourceSpec.supports()` 的文档里写清楚了。
- **P3-02** §51 的命令参数风格不统一。`mog source test example --fixture`
  传的是 ID，`mog source test .` 传的是路径。建议统一成"ID 或路径都接受"。
- **P3-03** §29 的 `GET /search` 没说是不是跨源。定成默认跨源并发，
  单源失败不影响整体，失败信息放在响应的 `errors` 字段里返回。
- **P3-04** 同一本书来自不同 source 时怎么处理，没提。
  建议放到 v0.5 之后做成"合并视图"，v1 不处理。
- **P3-05** 缺使用声明。开源爬虫类项目应该有明确的使用边界，
  现在加在 README 里了。
- **P3-06** §48 的 CI 矩阵里没有依赖漏洞扫描。建议加 pip-audit 或 Dependabot。

## 六、规划书没写但必须补的

这几条是实现过程中撞出来的，规划书完全没提到。

**错误的可重试标记。** §37 定义了错误层次，但没说哪些错误能自动重试。
如果重试策略里散落一堆 `isinstance` 判断，加一个错误类型就要改好几处。
给每个错误类加了 `retryable` 属性，重试策略直接读它。

**章节身份用候选键而不是单键。** §6.3 定义了优先级（sid → url → index），
按单键实现的话有个坑：书源某次更新后不再返回 `source_chapter_id`，
本地章节的主键是 `sid:c1`，远程草稿的主键是 `url:https://...`，两者不相等，
于是整本书被判定成全新章节，全部重下。改成候选键集合求交集就没这个问题。

**能力级 `url_join` 会误伤标题。** v1 的 `transform` 作用于能力下的所有字段。
如果无条件执行 `url_join`，`urljoin("https://site/search", "三体")` 会得到
`https://site/三体`，标题就毁了。改成保守判定：只有值"看起来像 URL 引用"
（以 `/` 开头、带 scheme、含 `/` 且无空白等）才拼接。这是 v1 的折中，
字段级 transform 放到 v1.1，那时候可以精确指定只对 url 字段执行。
原则是宁可漏拼，不可误拼。

**路径安全要分两种策略。** §40 只说"规范化，避免路径穿越"。
但书名里出现 `/` 是很正常的事（比如"上/下"），直接拒绝会让导出失败。
所以分成两个函数：`sanitize_component` 是宽容的，把非法字符替换掉，
用于书名作者这类元数据；`safe_path` 是严格的，遇到 `..` 或路径分隔符直接拒绝，
用于用户输入和书源提供的路径。

**文档解析必须先解码。** 上面 P1-05 提过，这里单列是因为它很隐蔽 ——
代码看起来完全正常，只是中文变成了乱码。

## 九、总结

规划书的质量比多数个人开源项目高。架构判断（API-First、声明式书源、严格边界）
是想过的，核心风险（兼容地狱、范围蔓延）也都识别到并主动规避了。

问题集中在工程细节的收敛度：多处"给了选项没选"、"提了要求没定义"、
"同一个概念几处写得不一样"。这类问题不影响架构正确性，但会实打实卡住开工 ——
因为每一个都要开发者临时做决定，而临时决定一旦落地就成了契约。

这轮把 P0 和 P1 全定了，写成四份规范。现在可以按 §60 的顺序往下推实现了。
